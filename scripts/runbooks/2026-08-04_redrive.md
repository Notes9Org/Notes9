# Runbook: chunk pipeline redrive — 2026-08-04

**HAND-RUN ONLY. DO NOT AUTO-RUN. Every SQL block below is MANUAL: run it
yourself in a psql / Supabase SQL editor session, read the preview counts, and
only then run the mutating statement.** No statement here belongs in a

Context: the queue accumulated (a) ~31 debris sources — `chunk_jobs` rows
pointing at content that was later deleted, (b) ~414 `status='failed'` jobs,
and (c) sources that have content but zero `semantic_chunks` rows. The root
causes are fixed by worker commits `b2b5e9a` / `e35819a` and the WP1
content-addressed path (migration 107 + `claim_chunk_jobs` /
`replace_chunks`), so redriving is now safe: retried jobs will not re-fail for
the original reasons.

Source-type → source-table map (derived from the enqueue triggers:
scripts/068, scripts/102, scripts/101, scripts/084):

| source_type          | source table               | notes                                   |
|----------------------|----------------------------|-----------------------------------------|
| `lab_note`           | `public.lab_notes`         |                                         |
| `literature_review`  | `public.literature_reviews`|                                         |
| `protocol`           | `public.protocols`         |                                         |
| `report`             | `public.reports`           |                                         |
| `experiment_summary` | `public.experiments`       | payload built by `experiment_summary_payload()` (102) |
| `chat_attachment`    | `public.chat_attachments`  | 7-day TTL (`expires_at`), soft delete (`deleted_at`) — 084/101 |

The worker reads content from `payload` (worker.py `payload.get("content")`),
so requeued jobs must carry a payload; step 4 copies each source's most recent
job payload, which is the content snapshot as of the last enqueue.

## 2. Delete debris chunk_jobs (source row no longer exists)

Scope: non-`delete` jobs in `pending`/`failed` whose source row is gone. A
pending `delete` job for a deleted source is *not* debris — the worker still
needs it to remove the chunks. `processing` rows are left alone (they are
claimed; stale claims are recovered by `claim_chunk_jobs` itself).

## 3. Reset failed jobs to pending — batches of 50

Run after step 2 so already-deleted debris is not resurrected. Repeat the batch
statement until it reports `UPDATE 0`. Batching (50) keeps row locks short so
the live worker's `claim_chunk_jobs` is never blocked for long.

```sql

```

```sql
-- MANUAL — MUTATING. Repeat until "UPDATE 0".
WITH batch AS (
  SELECT id
  FROM public.chunk_jobs
  WHERE status = 'failed'
  ORDER BY created_at
  LIMIT 50
  FOR UPDATE SKIP LOCKED
)
UPDATE public.chunk_jobs cj
SET status        = 'pending',
    error_message = NULL,
    retry_count   = 0,
    processed_at  = NULL,
    claimed_at    = NULL
FROM batch
WHERE cj.id = batch.id;
```

## 4. Requeue upsert jobs for zero-chunk sources

Scope: sources whose row still exists (and, for `chat_attachment`, is neither
expired nor soft-deleted), that have zero `semantic_chunks` rows, no
pending/processing job already, and whose latest job payload has usable
content (worker skips content < 50 chars — worker.py). The new job copies that
latest payload; `operation = 'update'` because the worker's update path
deletes-then-writes, so a retry never collides with partial rows (102 §3).

For `experiment_summary` specifically, re-running the §3 backfill in
`scripts/102_experiment_summary_enqueue.sql` is an equivalent alternative that
rebuilds the payload fresh (picks up linked-title drift); the generic requeue
below also covers it with the last-enqueued snapshot.

```sql
-- MANUAL — preview: zero-chunk live sources eligible for requeue, per type
WITH latest_job AS (
  SELECT DISTINCT ON (source_type, source_id)
         source_type, source_id, payload, created_by
  FROM public.chunk_jobs
  WHERE operation <> 'delete'
  ORDER BY source_type, source_id, created_at DESC
),
eligible AS (
  SELECT lj.*
  FROM latest_job lj
  WHERE length(coalesce(lj.payload ->> 'content', '')) >= 50
    AND CASE lj.source_type
          WHEN 'lab_note'           THEN EXISTS (SELECT 1 FROM public.lab_notes t          WHERE t.id = lj.source_id)
          WHEN 'literature_review'  THEN EXISTS (SELECT 1 FROM public.literature_reviews t WHERE t.id = lj.source_id)
          WHEN 'protocol'           THEN EXISTS (SELECT 1 FROM public.protocols t          WHERE t.id = lj.source_id)
          WHEN 'report'             THEN EXISTS (SELECT 1 FROM public.reports t            WHERE t.id = lj.source_id)
          WHEN 'experiment_summary' THEN EXISTS (SELECT 1 FROM public.experiments t        WHERE t.id = lj.source_id)
          WHEN 'chat_attachment'    THEN EXISTS (SELECT 1 FROM public.chat_attachments t   WHERE t.id = lj.source_id
                                                   AND t.deleted_at IS NULL AND t.expires_at > now())
          ELSE false
        END
    AND NOT EXISTS (SELECT 1 FROM public.semantic_chunks sc
                    WHERE sc.source_type = lj.source_type AND sc.source_id = lj.source_id)
    AND NOT EXISTS (SELECT 1 FROM public.chunk_jobs cj
                    WHERE cj.source_type = lj.source_type AND cj.source_id = lj.source_id
                      AND cj.status IN ('pending', 'processing'))
)
SELECT source_type, count(*) FROM eligible GROUP BY source_type ORDER BY source_type;
```
